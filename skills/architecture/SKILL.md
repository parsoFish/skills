# Architecture

Produce `docs/architecture/` (written) and `docs/reference/` (generated) for the project in the working directory, following the house style in [references/house-style.md](references/house-style.md). Never invent a fact: an unknown becomes a `GAP:` marker or an interview question.

## Stages

Run the three stages in order. Stage 1 is a program; stage 2 is one bounded review; stage 3 is what the person sees. Details: [references/flow.md](references/flow.md).

### Stage 0 — kickoff
1. `node scripts/arch/arch.mjs classify .` → archetypes and evidence. If `ambiguous`, keep going with the first kind and queue interview question `kind-ambiguous`.
2. If `docs/architecture/fold-rules.json` is missing, copy `assets/fold-rules.json` and adjust the component rules to the repo layout. Do not guess: read the manifests.

### Stage 1 — kit run (deterministic, no model calls)
Run `node scripts/arch/arch.mjs run .` It writes only under `docs/reference/` and `docs/architecture/_run/`:
- `reference/components.json` — folded import graph (tests excluded), edge counts, cycles.
- `reference/drift.json` — hand model vs code (runtime-tagged edges skipped).
- `reference/fitness.json` — rule results from `arch check`.
- `_run/gaps.json` — machine-detected gaps, each with a class: `kit`, `project`, `human`.

Then render for humans with LikeC4 using the legend in `assets/legend.c4` (kind colours, light theme, minor edges filtered):
```
npx --yes likec4@latest validate docs/architecture/model
npx --yes likec4@latest export png docs/architecture/model -o docs/reference/views --theme light --flat
```
The scaffold implements `classify`, `extract components`, `drift`, `check`; the other extractors (deps, delivery, extension points, api, tests, jobs, ui anchors) are listed in flow.md and produce the same JSON-plus-markdown pairs when implemented. Say which extractors ran and which did not.

### Stage 2 — agent review (bounded)
Read only agent-facing forms: `components.json`, `drift.json`, `fitness.json`, `gaps.json`, existing written docs. Then:
1. Seed or update `docs/architecture/model/hand.c4` from the generated graph plus the kind template in `assets/`; tag runtime-only relationships so drift skips them.
2. Draft or update the written docs the CHECKLIST for this kind requires (see house-style §3): overview, scenarios, journeys, loop, signals, secrets, risks, stakeholders, glossary, deps whys. Every non-code claim cites a file or ADR, or carries `GAP:`.
3. Classify every gap: `kit` (the tooling should have known — record it in `_run/kit-issues.md`, do not patch the project), `project` (the repo must change — list it in `review.md`, do not do it), `human` (write an interview question).
4. Check the registers against [references/completeness.yaml](references/completeness.yaml) and state unmet criteria as GAP lines in each file's header.
5. Write `_run/review.md` (what changed, confidence per file, project changes called out) and `_run/interview.md` using the question shape in [references/interview.md](references/interview.md).
6. Exit checks: no edits under `docs/reference/`; every written file under 400 lines; net lines reported; every gap classified.

### Stage 3 — present
Show the person rendered views (never `.c4` or JSON), the written docs, and `interview.md`. Record answers in `docs/architecture/answers.yaml` by question id. A re-run starts at stage 1 and re-asks only questions whose evidence changed.

## Rules that always hold
- Read-only on source code. Generated files carry a `generated by arch …` header and are never hand-edited.
- Humans see rendered views with the legend and a caption naming the question each view answers.
- Written docs: current-truth files are rewritten, history is appended and superseded (ADRs). Size cap 400 lines.
- Retired terms are linted, not remembered. Unknown facts are `GAP:` markers, never sentences.
