# Architecture

The kit ships inside this skill: every `arch` command below means `node <skill base directory>/scripts/arch/arch.mjs …`, where the base directory is the path shown when this skill loaded (never a path relative to the project). Produce `docs/architecture/` (written) and `docs/reference/` (generated) for the project in the working directory, following the house style in [references/house-style.md](references/house-style.md). Never invent a fact: an unknown becomes a `GAP:` marker or an interview question.

## Stages

Run the three stages in order. Stage 1 is a program; stage 2 is one bounded review; stage 3 is what the person sees. Details: [references/flow.md](references/flow.md).

### Stage 0 — kickoff
1. `arch classify .` → archetypes and evidence. If `ambiguous`, keep going with the first kind and queue interview question `kind-ambiguous`.
2. If `<docsDir>/architecture/fold-rules.json` is missing, copy `assets/fold-rules.json` there and adjust `rules`, `registries`, `kinds`, `titles`, `system` and `scanIgnore` (top-level directories that are not this project's code: archives, vendored checkouts, generated trees) to the repo layout. Run `arch classify . --help-fold-rules` for every field's shape, default and one example; do not read `model.mjs`/`walk.mjs` to work out the schema. Do not guess the values: read the manifests and the top-level tree.

### Stage 1 — kit run (deterministic, no model calls)
Run `arch run <root> [--out <docsDir>]`. The source tree is read-only; everything is written under `<docsDir>` (default `<root>/docs`). Use `--out` to document a repo without touching it (a scratch dir, or another checkout). Without `--out`, arch refuses to write into an existing `docs/` it does not manage (marker `docs/reference/.arch-managed`, created on the first managed run) — pass `--out` or create the marker to adopt a repo. Every later subcommand (`check`, `drift`, `extract`) takes the same `--out`; never omit it once you started with it.
Outputs, each JSON with a derived markdown twin under `reference/` (first line `generated by arch …`):
- `components` — folded import graph (tests excluded), edge counts, cycles; engine `builtin` by default (offline relative-import scanner), or `dependency-cruiser` when fold-rules set `"engine": "dependency-cruiser"` (resolves tsconfig paths, needs npx) · `drift` — hand model vs code (runtime-tagged edges skipped) · `deps` — ledger with whys inferred from import sites · `delivery` — workflow jobs, steps, gates · `extension-points` · `api` · `tests-by-seam` · `env` · `ui` · `fitness` — rule results · `completeness` — register criteria.
- `views/*.png` — LikeC4 renders with the legend (`assets/legend.c4`), light theme, minor edges filtered; the model text lives in `architecture/model/` (`spec.c4` = legend, `generated.c4` regenerated every run, `hand.c4` seeded once and never overwritten).
- `architecture/CHECKLIST.md` — required views for the kinds found, judged by shape (a diagram fence, the right table columns), not by file existence; missing required views read `MISSING`. ADRs are read from the source root's `docs/decisions` (or `docs/adr`, `adr`), and `decisions/README.md` is regenerated as the current-truth index.
- `reference/agent-map.json` + `architecture/AGENTS-ARCH.md` — the coding agent's map: component → owned paths → may import → must not import → proven by, then the rules that hold. Read this first when changing code.
- `reference/drift.md` — hand model vs code with a shrink-only baseline (`architecture/drift-baseline.json`): undeclared couplings count as drift; `arch drift` exits non-zero on unexplained drift so it can gate CI.
- `_run/index.html` — the human bundle as one self-contained page (rendered views with legend and captions, written docs, generated tables, interview), alongside `index.md`.
- `architecture/_run/gaps.json`, `questions.md` (kit-generated questions for human-class gaps not yet answered in `answers.json`), `kit-issues.md`, `project-changes.md`, `index.md` (the human-facing bundle; links `interview.md` once stage 2 has written it, else `questions.md`).
Run it twice if in doubt: the outputs are byte-identical for the same input.

### Stage 2 — agent review (bounded)
Guardrails, non-negotiable: **one reviewing agent, no subagents or forks**; **read `docs/architecture/_run/brief.md` first and only** — stage 1 writes it as the one file this stage has to read before writing anything; read a source file only to cite it, and **never read anything under this skill's own `scripts/` directory** — every rule, schema and fix recipe stage 1 could derive is already in the brief. If a rule is still unclear after reading it, record the gap in `_run/kit-issues.md` and take the brief's stated default; do not go look at the kit's code to find out. Write only under `architecture/` (except the final render step); never edit kit-owned files (`reference/`, `CHECKLIST.md`, `gaps.json`, `questions.md`, `generated.c4`, `spec.c4`). Before starting: `arch guard snapshot <root> --out <docsDir>`. After finishing: `… guard verify …` must pass — it fails if a kit-owned file changed or if an interview question is kit-shaped (extractor, regex, renderer) instead of an operator decision. **Budget: 120 turns** for a service-shaped repo under ~100 source files (evidence and the doc-set proportionality table for other sizes/kinds: [references/stage2.md](references/stage2.md)). Then:
1. **One `Write` per document — no reread-and-edit loops.** Draft each whole file in a single `Write`, in the order the brief's §5 checklist lists them, starting with `hand.c4`: seed or update `docs/architecture/model/hand.c4` once, before any other doc, recording every context edge and area membership the brief's §6 lists; tag runtime-only relationships so drift skips them. Keep every view readable: no `include *` in the containers view, at most 12 nodes per view, the components view keeps `exclude * -> * where kind is minor`. Never edit `CHECKLIST.md` or anything under `reference/`: fix the facts they derive from (fold rules, `answers.json`, the written docs) and re-run stage 1.
2. Draft the written docs the brief's §5 checklist requires, scaled to the project ([references/stage2.md](references/stage2.md) §proportionality — fewer, shorter docs for a smaller repo or a kind with fewer required views; never the full service-kind set by default). Diagrams for loop, signals, secrets and journeys are mermaid fences using the kit's `classDef` kinds; keep table cells under 220 characters and put rationale below the table. Every non-code claim cites a file or ADR, or carries `GAP:`. Record a new ADR only when a decision is evidenced in code or an existing doc — otherwise ask about it in the interview instead of inventing one.
3. Classify every gap the brief's §7 lists, plus any new one found while writing: `kit` (the tooling should have known — record it in `_run/kit-issues.md`, do not patch the project), `project` (the repo must change — list it in `review.md`, do not do it), `human` (write an interview question).
4. Revalidate once: `arch run <root> --out <docsDir> --no-render --now <date>`; fix only what the brief's §3/§4 recipes said, then run it once more at most. Extraction on a repo this size is seconds — this is not the slow step.
5. `arch guard verify` — must pass. Then write `_run/review.md` (what changed, confidence per file, project changes called out) and `_run/interview.md`: curate `_run/questions.md` (merge near-duplicates, drop anything answered, add questions the kit could not know) using the shape in [references/interview.md](references/interview.md). Stage 1 never overwrites `interview.md` or `review.md`.
6. `arch guard close`, then the single final `arch run <root> --out <docsDir> --now <date>` **with** rendering. **After `guard close`, nothing is edited** — no further `Write`, `Edit`, or re-run of `arch run` with different content.
7. Exit checks: `arch guard verify` passed; `arch check` passes; every written file under 400 lines; net lines reported; every gap classified; questions that are really kit issues moved to `kit-issues.md`. Finish with a short final message that lists every file produced, the gaps by class, and the open questions — that message is what a reader or grader sees first.

### CI
Add to the project's pipeline (read-only on source, writes only under `docs/`):
```
node <skill>/scripts/arch/arch.mjs run . --now $(date -u +%F)   # regenerate reference/, views, checklist, gaps
node <skill>/scripts/arch/arch.mjs drift .                       # exit 1 on unexplained drift (undeclared or claimed-but-absent edges)
node <skill>/scripts/arch/arch.mjs check .                       # exit 1 on rule failures (size caps, cited paths exist, view shapes, generated headers, retired terms)
```
Accepting a new coupling is an edit to `architecture/model/hand.c4` (declare it) or to `drift-baseline.json` (accept it, shrink-only) in the same PR, with an ADR when it crosses a boundary.

### Stage 3 — present
Open `_run/index.md`: rendered views first (never `.c4` or JSON), then written docs, then `interview.md`. Record answers in `docs/architecture/answers.json` as `{"<question id>": {"answer": "...", "at": "YYYY-MM-DD"}}`; `"answer": "n/a"` rules a gap out permanently (it stays in `gaps.json` as `accepted` and is never re-raised). A re-run starts at stage 1 and re-asks only questions whose id is not answered.

## Rules that always hold
- **Never stop to ask during stages 0–2.** There may be nobody to answer. A tool that cannot run (no network for LikeC4, a missing extractor, a denied permission) becomes a line in `run.md` and a `GAP:` in the affected doc; the run continues to the end and every question goes into `interview.md` for stage 3. Do not request network or elevated access mid-run.
- Read-only on source code. Generated files carry a `generated by arch …` header and are never hand-edited.
- Humans see rendered views with the legend and a caption naming the question each view answers.
- Written docs: current-truth files are rewritten, history is appended and superseded (ADRs). Size cap 400 lines.
- Retired terms are linted, not remembered. Unknown facts are `GAP:` markers, never sentences.
