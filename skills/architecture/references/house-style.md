# Architecture house style (condensed)

Generic to any software project by aligning with established architecture practice (ISO 42010 viewpoints, 4+1, SEI Views & Beyond, arc42, Well-Architected pillars, 12-factor, evolutionary architecture, Diátaxis, ADRs). Kinds are archetypes; named repositories are only evidence.

## Principles
1. One model, many views — a single LikeC4 model drives context, container, component, deployment and dynamic views.
2. Generate what can be generated; write only what cannot. Generated → `docs/reference/`. Written → `docs/architecture/`, `docs/decisions/`.
3. Current state is derived from the checkout, never remembered; every generated file carries `generated by arch <command>`.
4. Design and current state share one notation; drift is a diff, explained by an ADR or fixed in the model.
5. Fixed kind vocabulary (see `assets/legend.c4`): human · web UI · service/daemon · CLI · LLM agent · knowledge store · append-only log · workspace · external system · model API · IaC module.
6. A view exists only if a named stakeholder's concern needs it.
7. Deletion is first-class (bloat rules below).

## View set (question → view → generated or written)
| question | view | form |
|---|---|---|
| parts and what talks to what | C4 context + container | written model |
| what is inside, is it what we think | C4 component ⟵ import graph, drift diff | generated + overlay |
| where does it run | deployment view (device nodes for hardware) | written |
| how does scenario X move through it | dynamic view (numbered) or sequence | written, ≥ kind minimum |
| what events/schemas exist | schema & event catalogue | generated |
| HTTP or CLI surface | OpenAPI / `--help` reference | generated |
| what Terraform manages | module/resource graph | generated |
| why is it this way | ADR (Nygard) + generated current-truth index | written / generated |
| what could go wrong | risk & debt register | written |
| what a person does on the surface | screen-flow map anchored to DOM contract | written |
| how the loop ticks | tick-loop diagram with phase budgets | written |
| where others plug in | extension-point registry | generated |
| what emits what, who reads it | signals map | written, emitters extracted |
| how a change reaches main / prod | pipeline diagram with gates | generated |
| where secrets live and cross | credential flow with boundaries | written, names only |
| what we did not write and why it is here | dependency ledger | generated + annotated |
| which jobs run, in what order | job DAG | generated |
| what proves each seam | seam × layer test grid | generated |
| who cares about what | stakeholder–concern–view matrix | written |
| which rules hold everywhere | rule lint backed by a concept list | executable |

## Required views by archetype
CLI/library · service · IaC · plugin/provider · simulation/game · hardware · data pipeline · browser extension. Every archetype requires context+container, component+drift, pipeline, dependency ledger, ADRs+index, rule lint. Service adds deployment, ≥ 2 scenarios, catalogue, API, credential flow, signals, tests grid, risks, stakeholders. IaC adds the module graph, apply pipeline, credential flow, risks. Simulation and hardware add the tick loop; hardware adds device topology and signals. Pipeline adds the job DAG and data contracts. UI kinds add the screen-flow map. `CHECKLIST.md` records every required view as ✓, partial, or `n/a: reason`; blank is a failure.

## Layout per project


## Bloat and deletion rules
1. One current-truth file per topic; history is append-only + supersede.
2. A new ADR marks what it replaces `Superseded` in the same commit; the index is generated.
3. Written docs ≤ 400 lines; over cap = split or cut.
4. Reference docs are generated; a hand edit under `reference/` fails.
5. Retired terms are linted, not remembered.
6. Claims anchor to source paths; drift fails when the anchor moves and the doc does not.
7. Unknown facts get `GAP:`, never a sentence.
8. Every run reports net lines and files.
9. Dead-code tools per language run in `arch check`.
10. Guard-and-go and "docs only grew" are named defect classes.

## Audience rule
Humans see rendered views (legend colours, light theme, caption naming the question, ≤ 15 nodes, minor edges filtered) and markdown. Agents read `.c4`, JSON, mermaid source. Both forms come from the same command; the human form is derived, never hand-edited.

## Completeness
Registers are complete only against `completeness.json` criteria (kit defaults, project overrides). Unmet criteria appear as GAP lines in the register's header.
